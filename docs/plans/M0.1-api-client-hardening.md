# M0.1 — API Client Hardening & High-ROI Patterns

> Statut : À FAIRE  
> Type : dette technique à fort ROI  
> Dépend de : M0  
> À faire avant : M2/M4/M5/M6/M7 si possible, car ces jalons consomment fortement l'API.

## Origine

Analyse du repo `webkul/odoo-react-nextjs-commerce`.

Décision : ne pas reprendre le code directement. Le repo utilise l'API Frontend native d'Odoo, NextAuth, un checkout natif Odoo côté frontend, Tailwind v4 et un modèle e-commerce standard. Oaksome utilise une API custom `/api/oaksome/v1/*`, une session Odoo, `next-intl`, localStorage pour panier/wishlist avant checkout, et un configurateur métier.

Ce jalon reprend uniquement les patterns à fort ROI compatibles avec Oaksome.

## Objectif

Durcir la couche API frontend pour éviter la duplication, stabiliser les contrats TypeScript, normaliser les réponses Odoo, améliorer la validation des mutations, et rendre les futurs jalons plus rapides à implémenter.

## Non-objectifs

- Ne pas migrer vers l'API Frontend native d'Odoo.
- Ne pas introduire NextAuth.
- Ne pas changer le modèle localStorage du panier/wishlist.
- Ne pas copier les composants UI Webkul.
- Ne pas migrer vers Tailwind v4 ou Next.js 15.
- Ne pas modifier le contrat API sans mettre à jour `docs/api-contract.md`.

## État actuel à respecter

- Wrapper existant : `oaksome-web/src/lib/api/client.ts`.
- Types API basiques : `oaksome-web/src/lib/api/types.ts`.
- Services existants : `oaksome-web/src/lib/api/*.ts`.
- Proxy API Next.js : `oaksome-web/src/app/api/oaksome/[...path]/route.ts`.
- Contrat global : `/api/oaksome/v1/*`, paramètres `lang`, `country`, erreurs unifiées, pagination.

## Critères d'acceptation globaux

- Les appels API publics passent par un wrapper unique ou des helpers dérivés du wrapper existant.
- Les erreurs API sont typées avec `code`, `message`, `details?`, `request_id?` quand disponibles.
- Les paramètres globaux `lang` et `country` sont supportés de façon cohérente.
- Les endpoints critiques ont des operation types explicites.
- Les réponses des endpoints critiques sont normalisées avant d'atteindre les composants.
- Les mutations formulaire critiques utilisent Zod côté action/service avant appel Odoo.
- Aucun changement ne casse le contrat localStorage du panier/wishlist.
- `npm run type-check` et `npm run lint` passent.

## Tâches

### M0.1.1 — Auditer la couche API existante [S]

- [ ] Lister tous les modules dans `src/lib/api/*.ts`.
- [ ] Identifier les appels qui contournent `src/lib/api/client.ts`.
- [ ] Identifier les duplications de gestion `country`, `lang`, `revalidate`, erreurs, auth/session.
- [ ] Vérifier si les endpoints utilisent bien `/api/oaksome/v1/*` via le wrapper/proxy.
- [ ] Produire une courte note dans ce fichier sous `## Notes d'audit` avant modification.

**Portée** : `oaksome-web/src/lib/api/**`, `oaksome-web/src/app/api/oaksome/[...path]/route.ts`.

### M0.1.2 — Renforcer le wrapper API typé [M]

- [ ] Étendre `Result<T>` pour représenter l'erreur contractuelle Oaksome : `code`, `message`, `details?`, `request_id?`, `status`.
- [ ] Conserver la compatibilité avec les services existants qui testent `success`.
- [ ] Ajouter un type `ApiRequestOptions` avec `params`, `revalidate`, `tags`, `cache`, `headers` si nécessaire.
- [ ] Centraliser la construction d'URL avec `lang` et `country` sans imposer ces valeurs aux composants.
- [ ] Ne pas rediriger automatiquement dans le wrapper serveur. Limiter la redirection 401 au navigateur ou aux pages/actions dédiées.
- [ ] Préserver `credentials: 'include'` pour la session Odoo.

**Portée** : `oaksome-web/src/lib/api/client.ts`, `oaksome-web/src/lib/api/types.ts`.

### M0.1.3 — Ajouter les operation types API [M]

- [ ] Créer des types `Operation` pour les endpoints les plus utilisés.
- [ ] Commencer par : products, configurator, leads/contact, cart/checkout, auth/profile.
- [ ] Chaque operation doit déclarer `data`, `params?`, `body?`, `meta?` si applicable.
- [ ] Remplacer les types inline évidents dans les services concernés.

Exemple attendu :

```ts
export type GetProductsOperation = {
  data: Product[]
  params: {
    page?: string
    limit?: string
    country?: string
    lang?: string
  }
}
```

**Portée** : `oaksome-web/src/lib/api/operations.ts` ou fichiers par domaine dans `src/lib/api/*`.

### M0.1.4 — Introduire des normalizers de réponse [L]

- [ ] Créer un emplacement standard pour les normalizers.
- [ ] Ajouter au minimum : `normalizeProduct`, `normalizeCollection`, `normalizeConfiguratorOption`, `normalizeCart`, `normalizeApiError`.
- [ ] Les normalizers doivent protéger les composants contre : `null`, champs manquants, snake_case, tableaux absents, prix incomplets.
- [ ] Les normalizers ne doivent pas masquer les erreurs métier critiques comme prix absent au checkout.
- [ ] Appliquer les normalizers dans les services, pas dans les composants.

**Portée proposée** : `oaksome-web/src/lib/api/normalizers.ts` ou `oaksome-web/src/lib/api/normalizers/*.ts`.

### M0.1.5 — Standardiser validation Zod pour mutations [M]

- [ ] Identifier les mutations formulaire : contact, lead configurateur, échantillons, profile, checkout-url, auth.
- [ ] Ajouter les schemas Zod côté service/action pour les payloads critiques.
- [ ] Retourner les erreurs champ par champ dans un format stable.
- [ ] Ajouter un helper `resolveZodFieldErrors()` ou équivalent.
- [ ] Ne pas dupliquer la validation UI et serveur : l'UI peut prévalider, mais le serveur reste source de vérité.

**Portée** : `oaksome-web/src/lib/validation/**` ou `oaksome-web/src/lib/api/schemas.ts`, services concernés.

### M0.1.6 — Server actions uniquement pour mutations à ROI clair [M]

- [ ] Créer/standardiser des actions serveur pour : contact, lead configurateur, demande d'échantillons, update profile.
- [ ] Utiliser `useActionState` seulement pour les formulaires où l'état serveur améliore l'UX.
- [ ] Garder le panier/configurateur local en client state quand c'est exigé par le spec.
- [ ] Ne pas convertir tous les appels API en server actions par défaut.

**Portée** : `oaksome-web/src/app/[locale]/**/actions.ts` ou `oaksome-web/src/features/**/actions.ts` selon conventions existantes.

### M0.1.7 — Utilitaires sûrs et partagés [S]

- [ ] Ajouter ou consolider `isObject`, `isNonEmptyArray`, `createUrl`, `ensureStartsWith` si absents.
- [ ] Ajouter tests unitaires simples pour les utilitaires utilisés par la couche API.
- [ ] Ne pas ajouter de dépendance externe pour ces helpers.

**Portée** : `oaksome-web/src/lib/utils/**`, tests associés.

### M0.1.8 — Revalidation/cache compatible Next.js 14 [M]

- [ ] Ne pas utiliser les APIs Next.js 15 canary comme `use cache`, `cacheTag`, `cacheLife`.
- [ ] Utiliser uniquement `fetch(..., { next: { revalidate, tags } })` et `revalidateTag` si supporté par la version actuelle.
- [ ] Définir les tags minimum : `products`, `collections`, `configurator`, `cart`, `profile`, `content`.
- [ ] Documenter quels services sont ISR/cacheables et quels services doivent rester `no-store`.

**Portée** : `oaksome-web/src/lib/api/client.ts`, services API, éventuellement `docs/frontend-spec.md` si le comportement cache change.

## Risques

- Refactor trop large qui bloque les jalons fonctionnels.
- Normalizers trop permissifs qui masquent des erreurs backend.
- Confusion entre état localStorage intentionnel et état serveur Odoo.
- Usage accidentel d'APIs Next.js 15 non disponibles dans Next.js 14.

## Definition of Done

- La couche API est plus stricte sans changement fonctionnel visible.
- Les services critiques ont des types et normalizers explicites.
- Les formulaires critiques ont une validation serveur stable.
- Les futurs jalons peuvent consommer l'API sans réinventer erreurs, params, pays/langue, cache et validation.
- `npm run type-check` passe.
- `npm run lint` passe.
